# ระบบ Calibration + รายงาน — EC 3 ตัว (SEN0706)

เขียนตามระบบจริงที่ใช้อยู่: firmware **v8.3-3EC** + จอ ESP32-P4 + `calibration.py`

---

## 1. ภาพรวม — ใครทำอะไร

```
[จอ P4 สัมผัส] ──RS485 frame 0x21──┐
                                    ├──► [ESP32 v8.3] ──Modbus 0x0110──► [SEN0706 x3]
[Python: กด c ใน logger] ──C1,84──┘         │
                                             └── ตอบ "[cal] ok n=1 ..."
```

**ยิงคำสั่ง Modbus มีเจ้าเดียวเสมอคือ ESP32** — จอและ Python เป็นแค่คนขอ
บัสจึงไม่มีทางชนกันเชิงโครงสร้าง (นี่คือเหตุผลที่ไม่ให้ Python คุย RS485 ตรง ๆ)

**firmware ไม่ต้องแก้อะไรเลย** — คำสั่ง `C<n>,<uS>` และด่านกัน cal ตอนหัววัด
ไม่ได้จุ่มน้ำยา มีอยู่ใน v8.3 แล้ว งานที่เพิ่มทั้งหมดอยู่ฝั่ง Python

## 2. จุดคาลิเบรต: single point ที่ 84 µS/cm

| ทำไม | เหตุผล |
|---|---|
| ทำไมจุดเดียว | SEN0706 เก็บจุดคาลิเบรตได้จริงจุดเดียว จุดที่ 2 ทับจุดแรก (ยืนยันจากการทดลอง: cal 84 → อ่าน 84.0 เป๊ะ, cal 1413 ต่อ → กลับมาวัด 84 อ่านได้ 71.8) |
| ทำไม 84 ไม่ใช่ 1413 | wash endpoint จริงอยู่ 57–296 µS/cm — คาลิเบรตต้องอยู่ในช่วงที่ใช้งาน ไม่ใช่ปลายสูงของสเกล |

### เกณฑ์นิ่งเปลี่ยนเป็นสัดส่วน

เดิม `STABLE_SPREAD = 15 µS/cm` ตายตัว ซึ่งผูกกับการ cal ที่ 1413 (= 1%)
พอย้ายมา 84 µS/cm เกณฑ์เดิมกลายเป็น **±18%** คือหลวมจนไม่ได้กรองอะไรเลย

```python
STABLE_SPREAD_PCT = 0.02          # 2% ของค่ามาตรฐาน
STABLE_SPREAD_MIN = 1.0           # แต่ไม่ต่ำกว่านี้ (ความละเอียดหัววัด 0.1 µS/cm)
#   84 µS/cm  -> 1.68
# 1413 µS/cm  -> 28.26
```
ใช้ได้ทุกจุดโดยไม่ต้องแก้เลข — เปลี่ยนน้ำยาแล้วเกณฑ์ตามไปเอง

## 3. ใช้งาน

### ระหว่าง logger รันอยู่ (ทางหลัก)
```
กด [c] → เลือกตัว 1/2/3 → ใส่ค่ามาตรฐาน (Enter = 84) → ทำตามที่บอก
```
ไม่ต้องหยุด logger ไม่ต้องแย่ง port

### รันเดี่ยว (ตอน logger ไม่ได้รัน)
```bash
python calibration.py                      # ทำทีละตัวจนครบ 3 ตัว @ 84 µS/cm
python calibration.py --sensor 2           # เฉพาะ EC#2
python calibration.py --standard 1413      # จุดอื่น (ปกติไม่ต้องใช้)
```

### ขั้นตอนที่ควรทำ
1. ล้างหัววัดด้วยน้ำ DI **3 ครั้ง** (กัน KCl ค้างจากรอบก่อน)
2. ซับให้หมาด **อย่าเช็ดถูหัววัด**
3. จุ่ม **ทั้ง 3 หัวในบีกเกอร์เดียวกัน** — ระบบจะเก็บค่าอีก 2 ตัวไว้เทียบให้ด้วย
   ว่าตอนนี้ 3 ตัวอ่านตรงกันแค่ไหน (นี่คือตัวชี้วัดที่อยากได้จริง ๆ)
4. คนเบา ๆ ไล่ฟองอากาศ แล้วปล่อยนิ่ง

## 4. ไฟล์ที่ระบบเขียน

```
calibration_log.json                  ← ประวัติทุกครั้ง (แหล่งความจริง)
calibration_data/
├── cal_20260812_165300_EC1.csv       ← ค่าดิบทุก sample ของทั้ง 3 ตัว
├── cal_20260812_165300_EC1.xlsx      ← Summary + Trace ของครั้งนั้น
└── calibration_log.xlsx              ← สมุดรวม 1 แถวต่อครั้ง (ดู drift ข้ามเดือน)
```

### `cal_*.csv` — ข้อมูลดิบ
| คอลัมน์ | ความหมาย |
|---|---|
| `timestamp` | เวลาจริง (ละเอียดระดับมิลลิวินาที) |
| `elapsed_s` | วินาทีนับจากเริ่มคาลิเบรต |
| `phase` | `pre` = ก่อนยิงคำสั่ง, `post` = ตรวจซ้ำหลังยิง |
| `used` | `1` = ค่าที่ผ่านเกณฑ์นิ่งและถูกใช้ตัดสิน (คือค่าที่คิดสถิติ) |
| `EC1 EC2 EC3` | ค่าทั้ง 3 ตัว — เก็บทุกตัวเสมอ ถึงจะ cal ทีละตัว |

### `cal_*.xlsx` — ต่อครั้ง
- **Summary** — เวลา, ค่ามาตรฐาน, ก่อน/หลัง, ความคลาด, เกณฑ์ที่ใช้,
  **เวลาที่ใช้แต่ละขั้น** (รอนิ่ง / ยิงคำสั่ง+รอปรับ / ตรวจซ้ำ / รวม),
  และตารางสถิติ pre/post ของทั้ง 3 ตัว
- **Trace** — ค่าดิบทุก sample (ชุดเดียวกับ CSV)

### `calibration_log.xlsx` — สมุดรวม
1 แถวต่อการคาลิเบรต 1 ครั้ง: เวลา, ตัวไหน, มาตรฐาน, ผล, ก่อน/หลัง, ความคลาด,
n และ SD ทั้ง pre/post, RSD%, เวลาที่ใช้แต่ละขั้น, ชื่อไฟล์ trace

> สร้างไฟล์ใหม่ทั้งไฟล์จาก JSON ทุกครั้ง ไม่ได้ต่อท้าย — ถ้าไฟล์เสียหรือมีคน
> เปิดค้างไว้ ข้อมูลจะไม่หายเงียบ ๆ และไม่มีทางเกิดแถวซ้ำ

## 5. หน้า calibration ใน PDF

| รายงาน | หน้า | เนื้อหา |
|---|---|---|
| **รายตัว** (`sensor_N/EC*_session_*.pdf`) | 3 จาก 3 | เฉพาะ sensor ตัวนั้น |
| **รวม 3 ตัว** (`reports/run_3ec_*.pdf`) | 9 จาก 9 | ทั้ง 3 ตัว |

แต่ละหน้ามี 3 ส่วน:

1. **Calibration Details** — เวลา, ค่ามาตรฐาน, ก่อน/หลัง, ความคลาด, เกณฑ์นิ่ง,
   เกณฑ์ผ่าน, เวลาที่ใช้แต่ละขั้น + แถบผล **PASS / OUT OF TOLERANCE / FAILED /
   ABORTED / UNVERIFIED**
2. **Calibration Trace** — กราฟ EC เทียบเวลา จัดให้ `t = 0` คือจังหวะยิงคำสั่ง
   มีเส้นค่ามาตรฐาน และวงกลมรอบจุดที่ผ่านเกณฑ์นิ่ง (จุดที่ใช้คิดสถิติ)
   หน้ารวมซ้อนทั้ง 3 ตัว จัดเวลาให้ตรงกันที่จังหวะ cal ของแต่ละตัว
3. **Statistics** — n, Mean, SD, SE, RSD%, Min, Max, 95% CI
   (หน้าเดี่ยว = pre/post, หน้ารวม = 3 ตัวหลัง cal)

หน้ารวมมีแถบเพิ่ม: **Agreement between sensors** — บอก spread ระหว่าง 3 ตัว
และผ่านเกณฑ์ 3% ของค่ามาตรฐานไหม

> **ตัวเลขใน PDF กับใน Excel ตรงกันเป๊ะเสมอ** เพราะคำนวณจากไฟล์ trace เดียวกัน
> ด้วยฟังก์ชัน `calibration.cal_stats()` ตัวเดียวกัน และปัดค่าเป็น 0.1 µS/cm
> ตั้งแต่ตอนบันทึก (= ความละเอียดจริงของ register SEN0706) จึงไม่มี "ค่าจริง"
> สองเวอร์ชัน

**ถ้ายังไม่เคยคาลิเบรต** หน้านั้นจะขึ้นกล่องเตือน ไม่ทำให้รายงานพัง

## 6. ค่าตอน cal ไม่ปนกับข้อมูลการทดลอง

CSV เพิ่มคอลัมน์ที่ 11 `flag`:

| ค่า | ความหมาย |
|---|---|
| ว่าง | ข้อมูลการทดลองปกติ |
| `CAL` | เก็บตอนคาลิเบรต (หัววัดอยู่ในน้ำยามาตรฐาน) |

`report_3ec.py` และ `desktop_ui.py` ข้ามแถว `CAL` ให้เอง — กราฟการทดลองไม่มี
spike ลงไปที่ 84 แต่ข้อมูลดิบยังอยู่ในไฟล์ครบ

**CSV เก่า (10 คอลัมน์) ยังอ่านได้ปกติ** เพราะคอลัมน์ต่อท้ายและตัวอ่านใช้ตำแหน่ง 0–9

## 7. เกณฑ์ผ่าน/ไม่ผ่าน

| เกณฑ์ | ที่ 84 µS/cm | ความหมาย |
|---|---|---|
| นิ่งพอที่จะ cal | spread ≤ **1.68** µS/cm ใน 8 ค่าติดกัน | ค่านิ่งจริง |
| ผ่านหลัง cal | \|หลัง − มาตรฐาน\| ≤ 5% = **4.2** µS/cm | ตัวนั้น cal ติด |
| 3 ตัวตรงกัน | spread ≤ 3% = **2.52** µS/cm | เป้าหมายหลัก |

### ถ้าไม่ผ่าน — ไล่แก้ตามลำดับ
1. **ฟองอากาศ / คราบที่หัววัด** ← เจอบ่อยสุด → ล้าง DI ใหม่ คนไล่ฟอง แล้ว cal ซ้ำ
2. **น้ำยามาตรฐานเก่าหรือปนเปื้อน** → เปิดขวดใหม่ (84 µS/cm ดูดซับ CO₂ เร็วมาก)
3. **อุณหภูมิ 3 ตัวต่างกัน** → รอให้เท่ากัน (ดู T1/T2/T3 ใน CSV)
4. **ยังไม่ผ่านอีก** → เปิด `calibration_log.xlsx` ดูว่าตัวนั้น drift มากขึ้น
   เรื่อย ๆ ข้ามเดือนไหม ถ้าใช่คือหัววัดเสื่อม ควรเปลี่ยน

## 8. ทุกเส้นทางถูกบันทึกหมด

| ผล | เกิดเมื่อ | ยิงคำสั่ง cal ไหม |
|---|---|---|
| `ok` | ผ่านเกณฑ์ | ยิง |
| `out_of_tolerance` | cal แล้วยังเพี้ยนเกิน 5% | ยิง |
| `fail` | บอร์ด/หัววัดปฏิเสธคำสั่ง | ยิง แต่ไม่สำเร็จ |
| `unstable` | ค่าไม่นิ่งใน 120 วินาที | **ไม่ยิง** — กันไม่ให้ฝังความผิดพลาดถาวร |
| `unverified` | ยิงแล้วแต่อ่านซ้ำไม่ได้ | ยิง |

ทุกกรณีเขียน trace + Excel + ประวัติ — **ครั้งที่ล้มเหลวคือข้อมูลที่มีค่าที่สุด
ตอนไล่หาว่าหัววัดตัวไหนเริ่มเสื่อม**
