# สถาปัตยกรรม — ใครเป็นเจ้าของอะไร

## สามบอร์ด หนึ่ง PC

```
SEN0706 x3 ──RS485 4800 8N1──> CONTROL V1.2 ──USB CH340 115200──> PC (logger เดิม)
   addr 1,2,3                  (Modbus master ตัวเดียว)              │
                                                                     │ rec_status.json
ESP32-P4 Touch 1024x600 ──USB-Serial-JTAG 303A:1001 NDJSON──> PC (โปรเจกต์นี้)
        │                                                            │
        └── CH343 1A86:55D3 = log/flash ของคน  (คนละเส้น ไม่ปนกัน)   └─> data/events/
```

**ทำไมต้องสองเส้น USB จากจอ:** เส้น CH343 เป็น console ของคน มี log ปนตลอด
ถ้าใช้เส้นเดียวกันส่ง NDJSON จะต้องมี prefix framing และยังเสี่ยงหลุด
การใช้ USB-Serial-JTAG แยก ทำให้ **ไม่ต้องมี framing เลย** — หนึ่งบรรทัดคือหนึ่งเฟรม

## เจ้าของข้อมูล (P1)

| ข้อมูล | เจ้าของ | โปรเจกต์นี้ |
|---|---|---|
| raw CSV `water_data/` | logger เดิม | อ่าน (นับแถวแบบ incremental) |
| `rec_status.json` | logger เดิม | อ่าน |
| `sessions_3ec.json` | logger เดิม | ไม่แตะ |
| รายงาน PDF / Excel | `report_3ec.py` เดิม | ไม่แตะ · ไม่ import · ไม่ทำซ้ำ |
| การคาลิเบรต | `calibration.py` เดิม | ไม่แตะ |
| `data/events/*.jsonl` | **โปรเจกต์นี้** | เขียน (ต่อท้ายอย่างเดียว) |
| `display_mask` | จอ P4 | ตามจอ เว้นแต่ผู้ใช้สั่งคงค่า |
| `active_mask` (CONTROL โพลตัวไหน) | **ยังไม่มีใครเป็นเจ้าของ** | ส่งค่าสมมติ 0b111 + ธง |

## เธรด

| เธรด | ทำอะไร | ห้ามทำอะไร |
|---|---|---|
| main / UI | แสดงผล | ห้ามอ่านตัวแปรของ bridge ตรง ๆ — ใช้ `snapshot()` |
| `p4-bridge` | อ่าน NDJSON · เขียน event log · ส่ง state ทุก 3 วิ | **ห้ามแตะพอร์ต CONTROL** |
| (ระบบเดิม) | อ่าน serial CONTROL · เขียน CSV | — |

`_guard()` ห่อ `_run()` ทั้งก้อน — bridge ตายกลายเป็น `LINK_ERROR` ไม่ใช่โปรเซสตาย

## จังหวะเวลา (ตัวเลขมาจาก `pc_bridge.c` ไม่ใช่จากเอกสาร)

| ค่า | เท่าไร | ใครถือ |
|---|---|---|
| PC ส่ง state | ทุก 3 s | PC |
| จอถือว่า PC หาย | เงียบ > 10 s | จอ (`PC_STALE_MS`) |
| PC ถือว่าจอหาย | เงียบ > 10 s | PC (`offline_after_s`) |
| จอรอผลคำสั่ง | 5 s | จอ (`CMD_TIMEOUT_MS`) |
| คิว event ของจอ | 32 | จอ (`EVENT_Q_LEN`) |
| บรรทัดยาวสุด | 512 B | ทั้งสองฝั่ง |

**จอไม่ retry คำสั่ง** — PC จึงต้องตอบทุกคำสั่งเสมอ แม้เป็น NACK
การเงียบทำให้จอขึ้น "ไม่ทราบผล" ซึ่งชวนให้ผู้ใช้กดซ้ำ

## ความมีชีวิตของ logger เดิม — สามระดับ

**ตัดสินจากอายุของ "แถวล่าสุดใน CSV"** ไม่ใช่จาก `rec_status.json`

⚠️ `logger_3ec.py` เขียน `rec_status.json` เฉพาะตอนเปิดโปรแกรม · เริ่ม session ·
จบ session (บรรทัด 337, 403, 411) **ไม่ได้เขียนเป็นจังหวะ** ระหว่างเก็บข้อมูล
ปกติไฟล์นั้นจะเก่าขึ้นเรื่อย ๆ ตลอดกาล  ถ้าเอามาตัดสิน จะขึ้น
`PC LOGGER OFFLINE` ถาวรทั้งที่ CSV ยาวขึ้นทุก 2.5 วินาที และจะส่ง
`pc_online=false` ไปให้จอ ทำให้ผู้ใช้ที่หน้าจอเชื่อว่าไม่มีใครเก็บข้อมูล

`rec_status.json` ยังใช้ตอบว่า *session ไหนเปิดอยู่ · sample ชื่ออะไร*
ซึ่งเป็นคนละคำถามและไม่เกี่ยวกับความสด

| อายุแถวล่าสุดใน CSV | สถานะ | ข้อความ | `pc_online` ที่ส่งให้จอ |
|---|---|---|---|
| ≤ 10 s | ONLINE | `PC LOGGER ONLINE` | true |
| 10–30 s | STALE | `PC STATUS DELAYED` | true |
| > 30 s หรือไม่มีไฟล์ | OFFLINE | `PC LOGGER OFFLINE` | false |

ช่วงกลางคือ "ยังไม่รู้ว่าตายหรือแค่ช้า" การรีบบอกว่าตายทำให้คนวิ่งไปไล่สาย
ทั้งที่ไม่มีอะไรพัง — แต่พอเกิน 30 s ต้องบอกความจริง เพราะถ้าโกหกจอ
ผู้ใช้จะกด Save reading ต่อไปโดยเชื่อว่ามีคนรับ
